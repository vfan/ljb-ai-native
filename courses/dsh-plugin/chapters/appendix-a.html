TypeScript
function formatLabel(text: string): string {
  return `[提醒] ${text}`
}

formatLabel(42)   // 类型不匹配，编辑器会提示

类型检查只面对源码，不会校验用户、文件或网络传入的实际数据——那些输入仍需运行时校验（正课第 5 章的 Schema 就是运行时校验）。

A2

三种常见导入

TypeScript
import type { Context } from '@deepseek-ai/cordis'   // 只引入类型信息
import { defineTool } from '@deepseek-ai/dsh-tools'   // 引入运行时函数
import '@deepseek-ai/dsh-tools'                       // 副作用导入：加载模块/引入类型声明

导入模块 ≠ 启用对应服务：服务是否存在取决于运行配置和依赖机制（正课 4C）。

A3

模块与导出入口

模块通过导出公开能力、通过导入使用能力：

JavaScript
// greet.js
export function greet(name) {
  return `Hello, ${name}!`
}

// main.js
import { greet } from './greet.js'
console.log(greet('Ada'))

./greet.js 相对发起导入的文件解析。插件入口导出 apply，框架加载模块后按约定调用它并传入 ctx——导出了函数不代表它已经执行（正课第 3 章补完整链路）。

A4

包与 package.json

包是组织和分发代码的单位，可以包含多个模块、资源和配置：

文件作用
package.json包信息、入口和依赖声明
index.js / client.js入口（文件名不是固定规则，实际入口由声明决定）
JSON
{
  "name": "hello-example",
  "version": "0.1.0",
  "type": "module",
  "main": "./index.js"
}

type: module 表示按 ES 模块解释 .js 文件。按路径加载（./greet.js）与按包名加载（@deepseek-ai/dsh-tools）的解析规则不同——"找不到模块"时检查路径、安装位置、入口声明和运行环境。

A5

依赖的三类声明

声明用途
dependencies运行时依赖
devDependencies构建、类型检查、测试等开发依赖
peerDependencies声明与宿主配合提供的依赖及版本要求

某些框架包要遵循宿主的共享实例约定，否则插件可能加载另一份不兼容实现。peerDependencies 是依赖契约，不是"自动保证只加载一份"的开关——还要看包管理器和宿主怎么解析。本课程先用仓库开发环境，独立打包时再补依赖声明（正课第 8 章）。

A6

构建：从源码到分发文件

TypeScript 项目的典型结构：src/index.ts（开发源码）→ 构建输出 lib/index.js → package.json 的 main 指向构建输出。

纯 JavaScript 插件可以没有构建；但只要用到 TypeScript、打包或资源复制，就要把构建产物纳入交付。

入口必须与实际文件一致：声明 "main": "./lib/index.js" 而包里只有 src/index.ts，加载时找不到入口。要分别确认四件事：类型检查通过、构建成功、打包包含入口、宿主能加载——这是四个不同的验证结果。

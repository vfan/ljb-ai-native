CHAPTER 06 · CLIENT HALF / SLOTS / ROUTES

06

最小 Client 插件：
浏览器那一半

第一次写 Client 半区：把一个组件注册进插槽，并让它显示 Host 的数据。

前 5 章你写的全部是 Host 侧代码；本章第一次写 Client 半区，并完整走通七环节图的第 7 格：展示。

素材来自课程自带的 hello-dsh 示例（一个双半区最小插件）。本章在它的基础上做三步改造，而不是从零开始——读契约、改组件、加通信。

第 1 节

要解决的问题

第 5 章说了"插槽注册决定组件显示在哪里"，但你还没亲手注册过。学完本章你应该能：

  1. 独立说出 Client 半区从哪里被加载（dsh.client 声明 + 模块加载器）。
  2. 把一个组件注册到 conversation.composer.dock（输入框卡片下方的环境信息带）。
  3. 让这个组件显示 Host 侧的一个计数——这逼你走一遍 Client 与 Host 的通信，不通信就只是个静态徽章。

第 2 节

核心概念

1. 双半区插件的文件结构

以 hello-dsh 为例：

文件半区作用
package.json—dsh.bundle.patch 声明配置层；dsh.client 声明浏览器半区
cordis.patch.yml—把插件行插入当前 profile
index.jsHost导出 apply(ctx, config)（本示例为空实现）
client.jsClient调用 window.__ModuleLoader__.load() 注册浏览器模块
locale/*.json、icon.svg—插件页显示的标题、描述和图标

dsh.client 里的关键字段：

JSON
"client": {
  "platform": "web",
  "immediately": true,
  "inject": ["@deepseek-ai/dsh-client-ui-conversation"]
}
  • platform: web：这是 Web 前端的 Client 模块。
  • inject：声明需要的客户端宿主包（这里是会话界面），提供 React 和插槽声明。
  • React 来自宿主的浏览器模块表，绝不能在插件里再打包一份——两份 React 会导致 hooks 报错。

2. Client 入口的注册三件事

client.js 的骨架：

JavaScript
window.__ModuleLoader__.load({
  id: '@local/hello-dsh',          // 必须等于包名
  factory(require) {
    const React = require('react')   // 从宿主模块表取，不要自己打包
    // ...组件定义...
    return {
      inject: ['slots'],
      apply(ctx) {
        ctx.slots.inject('conversation.composer.dock', () =>
          ctx.slots.register(
            { name: 'conversation.composer.dock', id: 'hello-dsh', order: 5 },
            HelloBadge,
          ),
        )
      },
    }
  },
})

对照第 5 章的三个不要混：

  • inject: ['slots'] 是服务依赖；
  • ctx.slots.inject(name, cb) 等宿主声明该插槽后再执行（解决时序）；
  • ctx.slots.register({ name, id, order }, Component) 才决定位置。

注意 Client 半区同样有 inject / apply 结构——这是同一套 Cordis 约定跑在浏览器里，只是能力表不同（有 slots，没有 node:fs）。

3. conversation.composer.dock 为什么是这个徽章的家

该插槽的契约定义（见 ui-conversation 的 contract/slots.ts）：输入框卡片下方、与输入框同宽的一条带，list 类型、session 作用域，适合放"会话状态、统计、提示"这类不需要用户操作的环境信息。徽章是环境信息，放这里；一个主操作按钮则应考虑标题栏的 conversation.session.header.actions。

第 3 节

操作与预期结果

以下三步，每步重启后在浏览器验证，打开开发者工具 Console——Client 的错误和日志都在那里（对照第 2 章的日志表）。

第 1 步：跑通原版徽章

参照 hello-dsh/README.md，把它作为 bundle 安装/加载（或按你的环境用 --patch 指到本地目录），启动 Web 前端后确认：

  • 输入框下方出现 "Hello DSH" 徽章；
  • 点击后计数 +1（Hello DSH · 3）——这是纯 Client 状态（React.useState），没有经过 Host；
  • Console 无报错；卸载插件后徽章消失。

这一步验证：dsh.client 声明 → 模块加载器 → apply → 插槽注册，整条链路通。

第 2 步：读契约，换一个位置

把注册目标从 conversation.composer.dock 改成 conversation.session.header.actions（先到契约文件确认它接受 list、session）。刷新页面后徽章应出现在会话标题旁。

再做一次反向验证：把 name 改成一个没有声明的字符串（如 'right.top.corner'），观察现象——插槽名不是任意字符串，没有声明的名字不会成为位置。

第 3 步：让徽章显示 Host 的计数

现在徽章的计数是浏览器自己的 useState。真正的双半区插件要把 Host 侧的数据送到 Client。最小改造方案：

  1. Host 半区（index.js）监听 tools/result 计数（复用第 4 章的 tool-logger 逻辑），并通过 Web 路由暴露，例如 GET /my-counter/value 返回 { count }（路由注册方式参照官方 webServer 服务文档；这是第 7 章案例中 Host 四路由的微缩版）。
  2. Client 组件用 fetch('/my-counter/value') 拉取，显示到徽章上（定时轮询或点击刷新各有利弊，实现时权衡实时性与请求量）。
  3. 调用一次 greet 工具，刷新页面——徽章应显示新计数。

做完这一步你就独立走过了真实案例（第 7 章）里"两端通过路由和配置命名空间连接"的全部要素，只是规模缩小：两端各写一份路由字符串常量，必须一字不差。

第 4 节

常见问题

现象优先检查
徽章完全不出现Console 是否有加载错误；dsh.client 是否声明；id 是否等于包名
组件报 React hooks 错误插件是否自己打包了 React（不允许）
注册到未声明插槽后无反应插槽名是否来自目标契约文件
Host 路由 404路由路径两端是否一致；Host 半区是否真的执行了注册

第 5 节

练习

  1. 徽章的点击计数和第 3 步的 Host 计数，分别是什么——配置、Client 状态还是 Host 状态？（对照第 5 章）
  2. 为什么 require('react') 不会装第二份 React？如果自己 import 一个打包过的 React 会怎样？
  3. 把徽章从"显示 Host 计数"改成"点击时清零 Host 计数"，通信方向发生了什么变化？需要 Host 增加什么？
  4. 卸载插件后，浏览器里残留了什么？Reload 页面前后分别检查。

本章带走句

Client 是同一套 Cordis 约定跑在浏览器里——位置来自插槽契约，数据来自与 Host 的显式通信；两端没有共享内存，路由字符串两端各写一份、必须一字不差。

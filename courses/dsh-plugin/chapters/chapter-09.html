综合项目：
工具调用计数器

从写、配、验、包、装到卸，完成一个范围清楚、能验证的综合项目。

毕业项目。覆盖七环节图的全部 1–7 格：写、配、验、包、装、卸，并按明确的三档评分标准交付。

七环节
1安装2加载3初始化4注册5触发6执行7展示

第 1 节

任务与统计契约

做一个工具调用计数器：插件启动后，记录其监听范围内各工具结果出现的次数，按工具名称在终端输出。

输出
[工具统计] greet：第 1 次
[工具统计] greet：第 2 次
[工具统计] another_tool：第 1 次

统计契约（每个插件都应能用一句话说清自己不做什么）：

本插件统计当前 Host 插件实例存活期间，在其可见事件作用域内收到并通过过滤条件的 tools/result 回调次数，按工具名称累计。不区分会话，不恢复历史，不代表业务成功次数。重启后归零；重载时旧监听撤销，新实例从零开始。

基础版按插件实例计数，不区分会话和 Agent——同一 profile 下多个会话或子 Agent 的工具结果会进入同一个 Map。如果只统计当前会话，需要从事件参数取会话标识并分组（属于扩展方向）。

第 2 节

核心概念

执行流程

flowchart TD
    A["插件加载与配置校验"] --> B{"功能启用？"}
    B -->|否| C["结束初始化"]
    B -->|是| D["创建计数状态并注册监听（只执行一次）"]
    D --> E["等待下一次工具结果"]
    E --> F["收到工具结果"]
    F --> G{"符合过滤条件？"}
    G -->|否| E
    G -->|是| H["更新该工具次数并输出"]
    H --> E

先过滤，再计数；D 只执行一次，H 之后回到等待，不会重新初始化。

状态的形状与重载边界

按工具名称保存次数（greet 为 2、another_tool 为 1），而不是共用一个总数。重载时旧实例监听被撤销、新实例从零开始，后续事件不会被新旧两个监听重复处理。跨重载保留计数、历史去重都不在本项目范围内。

第 3 节

实现与验证

第一步：只验证加载

入口先只输出一行 [工具统计] 插件已加载。看到它说明第 2–3 格通过，再加功能。

第二步：观察工具结果

TypeScript
ctx.on('tools/result', (exec) => {
  console.log(`${config.prefix} 收到：${exec.name}`)
})

用一次真实调用确认监听生效、一次调用只产生一条记录。

第三步：完整实现

TypeScript
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'
import '@deepseek-ai/dsh-tools'

export const name = 'tool-counter'

export interface Config {
  enabled: boolean
  prefix: string
  onlyTool: string
}

export const Config: Schema<Config> = Schema.object({
  enabled: Schema.boolean().default(true),
  prefix: Schema.string().default('[工具统计]'),
  onlyTool: Schema.string().default(''),
})

function increment(counts: Map<string, number>, toolName: string): number {
  const next = (counts.get(toolName) ?? 0) + 1
  counts.set(toolName, next)
  return next
}

export function apply(ctx: Context, config: Config) {
  if (!config.enabled) {
    console.log(`${config.prefix} 统计已关闭`)
    return
  }

  const counts = new Map<string, number>()

  ctx.on('tools/result', (exec) => {
    if (config.onlyTool && exec.name !== config.onlyTool) {
      return
    }
    const next = increment(counts, exec.name)
    console.log(`${config.prefix} ${exec.name}：第 ${next} 次`)
  })

  console.log(`${config.prefix} 插件已加载`)
}

increment 不依赖 dsh，可单独测试；counts 与监听都在 apply 内创建，每个实例各自从零开始。

验证矩阵

一张成功截图不说明正确。每个场景区分一种错误实现：

场景预期能发现的问题
连续调用两次 greet次数为 1、2是否真正累计
调用两种工具分别计数是否错用单一总数
只统计 greet，再调其他工具其他不计数过滤是否在计数前
enabled: false无输出开关是否有效
改前缀后重启用新前缀是否读真实配置
重启实例从 1 重新开始状态生命周期
热重载旧实例停输出、新实例从 1 开始、无双份日志旧监听是否撤销

验收时区分三种"两次"：模型说自己调用了两次、实际出现两次工具执行记录、插件记录了两次——以执行证据为准。

故障演练：故意制造三个问题（先做坏，再做对）

问题一：过滤后次数不对。 把计数写在过滤之前——表面不输出其他工具，内部却统计了它们。修复原则：先判断是否统计，再改状态。

问题二：所有工具共享次数。 用单一 let count = 0，无法表达各工具的次数。

问题三：一次调用输出两条日志。 先查重复来源（两个条目加载同一插件、源码版+安装版并存、重复监听、自建订阅没清理），不要在输出里加"去重"——可能把真实调用也过滤掉。

第 4 节

交付与评分

按第 8 章流程打包为可安装 bundle，提交前核对：

内容要求
代码入口、配置、计数、监听逻辑可定位
安装包可从 .tgz 安装并运行
使用说明安装、启动、配置、卸载方式 + 一句话统计契约
版本记录实际验证过的 dsh 版本或提交
验证记录验证矩阵逐项结果
问题记录至少一个问题的定位与修复过程

评分标准（三档）：

档位描述对应比重思路
合格验证矩阵全绿：日志与预期逐项对得上，安装/卸载路径走通功能正确 35%
良好在合格之上，能解释每个注册在卸载时的撤销时机、配置与状态的归属、每条日志来自哪个环节机制理解 25%
优秀在良好之上，能主动说出自己实现的两个以上边界（如多会话混入同一 Map）、故障演练能独立定位、说明文档写清"不做什么"调试 20% + 交付 20%

不以代码行数或功能数量评价。一个范围清楚、正确运行的小插件，比堆功能却解释不了的项目更有价值。

使用 AI 生成代码时

可以让 AI 出初稿、解释类型错误、分析日志，但事件名与签名、配置字段是否接入逻辑、清理是否对应真实资源、压缩包内容、安装 profile，都要逐项核对。解释不了触发路径的代码不要提交。

第 5 节

复盘问题

  1. 为什么这个需求适合用插件，而不是让模型事后总结？（对照第 1 章触发机制）
  2. 哪个配置让 dsh 加载它？——答两层：包的 dsh.bundle.patch 让它成为一个配置层；cordis.patch.yml 的 insert 让它以条目进入配置树。
  3. 哪段代码加载时执行？哪段在工具结果出现后执行？
  4. 配置与计数状态分别在哪里？ctx.on 的监听和 counts 各自怎么消失？（监听由上下文生命周期回收；counts 随实例一起消失，不需要手动清理）
  5. 结果不符预期时，第一步检查什么？（答：先定七环节图的第几格）
  6. 加"查询统计"工具时，它自己算不算被统计？ 两种设计各有立场——计入：口径一致，"工具调用次数"无需特判，简单且不会自欺；不计入：统计目标是"业务工具的使用情况"，自身查询属于观测行为，混入会污染数据。关键不是选哪个，而是：选了就写进统计契约，让数字可解释。

调试、打包
与分发

把七环节图展开成排障流程，再把插件打成可以交给别人的包。

本章把第 2 章引入的七环节图展开成完整排障流程，并走通它的最后一块：第 1 格，安装。学完本章，你的插件就能交到别人手上。

七环节
1安装2加载3初始化4注册5触发6执行7展示

第 1 节

要解决的问题

插件没有正常工作，怎样定位？本地开发完成后，怎样让别人安装？

调试的目标不是猜原因，而是找出最早一个没有证据证明成功的环节。（回忆第 2 章主图：）

环节要确认的问题
1 安装包和相关文件是否存在？
2 加载当前运行配置是否引用了插件？
3 初始化入口是否执行，依赖是否就绪？
4 注册工具、监听或界面是否成功注册？
5 触发是否发生了预期的调用或事件？
6 执行程序是否完成操作？
7 展示结果是否返回到正确位置？

"没有听到提示音"只描述最终现象；从最早一个没有证据的环节开始查。插件在本地源码正常、安装后失败，就先查第 1、2 格，而不是重写业务逻辑。

环境区分：pnpm dsh ... 在源码 checkout 根目录；已安装 CLI 用 dsh ...；桌面 App 走界面。三种入口不要混写成同一条命令。

第 2 节

核心概念

用日志建立执行证据

不要只在报错后输出日志，在关键边界留简短标记：入口、事件入口、过滤分支、返回结果。放太多反而难读。处理真实数据时，不要输出完整凭据、文件内容或用户隐私。

实际输出优先判断
没有"入口执行"第 2–3 格有问题
只有"入口执行"没发生事件，或监听契约有问题
出现"已忽略"过滤条件不匹配
进入处理后失败查第 6 格的后续逻辑

区分宿主错误与浏览器错误

位置优先查看
Host启动终端、宿主日志
Client浏览器 Console
网络通信浏览器 Network、宿主路由日志
安装与构建对应命令的输出

用最小复现隔离问题

版本保留内容验证目标
A只有入口日志第 2–3 格：模块能否加载
B加入服务依赖第 3 格：依赖能否满足
C加入状态订阅第 5 格：能否收到变化
D加入播放逻辑第 6 格：能否执行
E恢复设置界面第 7 格：交互是否正常

常见故障 → 排查方向

现象常见原因卡在哪格
找不到模块路径错误、包缺失、入口未导出1–2
插件一直不执行必需服务未提供（inject）3
工具没被调用不可用、描述不匹配、模型直接回答5
配置修改无效改错 profile、被后层整体替换2
操作执行多次重复条目、重复监听、清理遗漏4
界面没显示Client 未加载、插槽不匹配7
本地正常安装后失败缺产物或缺依赖1
升级后失败宿主契约变化4

第 3 节

操作与预期结果

从绝对路径到可安装的包

绝对路径只适合当前机器。分发时让用户安装一个包，通过包名找到入口。用纯 JavaScript 最小例子（排除构建影响），三个文件各司其职：没有入口，加载找不到代码；没有补丁，装上也不会进入运行配置。

1. 创建最小插件（仓库根目录）：

hello-plugin/index.js：

JavaScript
export const name = 'hello-plugin'

export function apply() {
  console.log('[hello-plugin] 安装版插件已加载')
}

hello-plugin/package.json：

JSON
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "./index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}

hello-plugin/cordis.patch.yml：

YAML
- insert:
    - id: lesson-installed-hello
      name: dsh-hello-plugin

dsh.bundle.patch 告诉 dsh 这个包提供一层配置；补丁引用的是包名，不再是作者机器上的路径。

2. 安装到独立 profile：

Terminal
pnpm dsh plugin --profile lesson-pack add ./hello-plugin
pnpm dsh --profile lesson-pack --dump-config   # 输出应含 dsh-hello-plugin
pnpm dsh --profile lesson-pack

终端出现 [hello-plugin] 安装版插件已加载 即安装+加载验证通过。

这个 profile 只验证 Host 日志，不验证 Web 页面。 新建插件 profile 默认以 base 组合为基础，不含 Web/TUI 前端，不会出现页面；看到日志后 Ctrl+C 结束即可。需要界面的验证（如第 6 章的插件）另配包含 Web 能力的组合。安装与启动必须用同一个 profile；独立 profile 也不隔绝机器级配置，异常时仍要检查叠加。

3. 用压缩包验证交付内容。 本地目录安装可能链接到开发目录，意外用到没打包的文件；压缩包验证才检查实际交付内容：

Terminal
cd hello-plugin && pnpm pack
tar -tf dsh-hello-plugin-0.1.0.tgz   # 应含 package.json、index.js、cordis.patch.yml
cd ..
pnpm dsh plugin --profile lesson-tarball add ./hello-plugin/dsh-hello-plugin-0.1.0.tgz
pnpm dsh --profile lesson-tarball

4. TypeScript 插件的打包前检查：构建已完成；main/exports 指向存在的文件；files 含构建产物及必要资源；运行依赖声明完整；压缩包安装不依赖原源码目录。只写 "main": "./lib/index.js" 不会自动生成产物。

5. 三种分发方式：

方式适合场景重点
.tgz 压缩包小范围交付直接验证实际产物
npm 包持续发布包名、版本与发布内容
Git 仓库源码协作构建产物与安装脚本（仓库带 build 不代表安装时执行）

6. 版本兼容声明：记录实际验证过的版本：

JSON
{ "engines": { "dsh": "0.1.1-rc.1" } }

课程基线 0.1.1-rc.1 中，engines.dsh 只作兼容声明，安装器和加载器不强制拦截；其他版本行为可能不同，请在实际使用的版本上核对，不要外推。普通 SemVer 范围可能不包含预发布版本：写精确版本，或显式包含预发布。升级时保留上一份可用安装包以便回退。

7. 卸载并验证：

Terminal
pnpm dsh plugin --profile lesson-pack remove dsh-hello-plugin

再启动对应 profile，确认日志不再出现。卸载代码 ≠ 删除用户数据：真实插件可能留下配置或数据，应在说明中写清楚。

第 4 节

练习

把最小插件改成"启动信息插件"，输出版本号从 package.json 读取（不要在入口里硬编码会漂移的版本号）。完成：本地目录安装 → 打包并检查内容 → 压缩包安装验证 → 卸载验证 → 编写简短说明（安装命令、适用版本、日志位置，以及卸载后保留什么）。

说明要让别人照做时能判断每步是否成功：安装后日志出现，卸载后日志消失。

本章带走句

排错就是给七环节图找证据——从最早一个没有证据的环节查起；交付验证以压缩包为准，因为本地目录跑通≠交付物跑通。

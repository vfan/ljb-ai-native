本章是只读案例：不要求把这个插件跑起来。 案例插件 dsh-plugin-notify-sounds@v1.9.2 与课程源码基线 0.1.1-rc.1 不保证接口兼容——"代码读得通"不等于"加载得起来"，运行与安装验证的方法在第 8 章专门学习。

第 1 节

要解决的问题

一个已发布的声音通知插件，代码分在 Host 和 Client 两个入口。逐行读文件会得到很多局部结论，却回答不了：

  • 任务结束时，哪段代码最先发现状态变化？
  • 浏览器里播放声音的是谁，把窗口抬到前台的又是谁？
  • 用户拖动音量，值最终写到了哪里？
  • 插件重载或卸载时，哪些工作必须撤销？

项目地址：dsh-plugin-notify-sounds（固定读 v1.9.2）。

第 2 节

核心概念

1. 阅读路线：先回答六个问题

拿到一个插件项目，不必逐行读到底：

问题优先查找对应环节
从哪里加载？package.json、配置补丁1–2
入口在哪里？apply、模块导出3
依赖什么？inject、导入语句3
注册了什么？工具、事件、服务、UI4
谁来触发？模型调用、状态变化、用户操作5
如何清理？ctx.effect、取消订阅、销毁函数卸载

2. 文件性质：发布产物，不是开发源码

该仓库没有单独的 src/；lib/client.js、lib/index.js 是随包发布的运行代码，保留了注释和模块结构，适合研究行为，但不是作者的开发源码。package.json 的 exports 给出两个入口：lib/index.js（Host）与 lib/client.js（Client）；清单里的 dsh.bundle.patch 参与加载配置，客户端包依赖声明与代码里 inject 的服务名属于不同层面。

3. Host 半区：五件浏览器做不到的事

lib/index.js 主要做五件事：

职责位置说明
提供配置 schemaConfig + applySettings 按 notify-sounds 命名空间提供；Client 通过 configForms 读写
处理通知点击/notify-sounds/focusClient 在系统通知被点击时 POST；Host 抬窗
检查更新/notify-sounds/update/check只查询 npm 最新版本，不写文件
查询目标阶段/notify-sounds/goal?session=...从 projection 读取会话的 goal phase
存储自定义音频/notify-sounds/sound按内容哈希存取 profile 下自己的目录

Host 在 apply 中注入 settings、webServer、connection，每条路由处理前先 connection.requestRejection(req) 检查请求来源。/notify-sounds/sound 用了 node:fs，但只操作自己 profile 下的目录——它不是 ctx.fs 示例的替代品（对照第 2 章文件访问边界）。

4. 两端通过路由和 configForms 连接

连接点Client 侧Host 侧
配置ctx.configForms.get("notify-sounds")Settings 提供同命名空间 Config
通知点击fetch("/notify-sounds/focus", POST)抬升窗口
目标阶段 / 音频 / 更新各自 fetch(...)对应路由

配置链路：Host 的 Config 由 Settings 按命名空间提供 → Client 用 configForms.get 取得表单 → form.set 写回。Client 不直接改 Host 的内存对象。

两端必须一致的四项（第 6 章第 3 步你已经亲手做过这件事）：

  1. 路由字符串（两端各写一份常量）；
  2. 配置命名空间（notify-sounds）；
  3. 配置字段名（任一侧改名，另一侧读到空值）；
  4. 音频标识（预设与自定义槽位的 id 列表）。

Client bundle 自包含、不能 import Host 代码，所以两边各写一份；改任意一侧，另一侧必须同步。

停靠点 1：合上材料，讲一遍"用户点击系统通知 → Host 抬窗"的完整链路，每一步落到函数名或路由名。讲不出回看 二.3–二.4。

5. Client 主循环：比较状态快照

Client 的核心路径：读取状态快照 → 与上一次比较 → 判断是否需要提醒。在 lib/client.js 里从 source.subscribe / sessionStatus 开始搜，再找 previous、handleCompletion 定位这条链。

核心判断只有一处：

JavaScript
if (
  before !== undefined &&
  before.running === true &&
  status.running === false
) {
  handleCompletion(sessionId, form.getSnapshot().value);
}

三个条件缺一不可：before !== undefined 处理第一次读取；before.running === true 排除历史空闲会话（否则每次刷新都会把早已结束的会话当"刚完成"再次提醒）；status.running === false 表示这一轮刚停下。只看当前状态回答"现在是什么"，状态变化回答"刚刚发生了什么"——写成 if (!status.running) 是新手版错误。

注意：这里识别的只是运行状态变化，进入 handleCompletion 后还要按提醒策略决定，不能把这个条件等同于"业务任务成功完成"。

6. 提醒分层与去重

发现新的待处理交互后，实现为每个交互保存：交互对象、出现时间、上次提醒时间、是否已看过、出现时是否处于静音时段。用户返回页面后标记"已看过"——这里有一个产品判断：用户已经看到问题，即使尚未回答，也不再重复催促。状态字段和判断条件往往承载产品规则。

7. 声音在哪一端播放、以及"没有声音"的五层原因

audioEngine、playSound、whenRunning、releaseAudioEngine 围绕浏览器音频环境；实现还处理了音频环境尚未启动的情况（浏览器可能要求用户交互后才允许播放，对照第 2 章）。

"没有声音"可能来自不同层次：

层次可能原因
状态检测没检测到符合条件的变化
提醒策略静音时段或开关阻止
多页面协调当前页面不是负责提醒的页面
浏览器音频音频环境尚未允许播放
音量与资源音量设置或自定义音频有问题

沿这条路径检查，比反复修改播放函数有效。

停靠点 2：不看代码，从"用户切到其他窗口"讲到"Host 抬升窗口"，每一步落到函数名或路由名。讲不下去的位置就是需要回去补读的位置。

8. 设置界面注册与清理

  • 注册：ctx.slots.inject("settings.section", ...) + register({ name: "settings.section", id: SETTINGS_NAMESPACE, order: 5 })；order: 5 把页面放在该版本布局的 General 与 Models 之间——位置来自注册契约和排序规则，与代码目录叫什么无关。注册包在配置命名空间的可用性门控里：命名空间没被 Host 提供时，整个设置分区不出现（避免"界面存在、背后配置能力缺失"）。
  • 写路径：setField: (field, value) => form.set(field, value)（改配置）与 preview: (id, volume) => playSound(...)（立即试听）。试听不经过模型，是用户界面直接触发的程序行为（对照第 1 章触发方式表）。
  • 清理：unsubscribe()、clearInterval(renotifyTimer)，另加其他订阅、监听、观察器和音频引擎释放。对照第 3 章带走句：这里清理的全是"自己开"的资源。

停靠点 3：说出四条 Host 路由分别由 Client 的哪个动作触发；说出 Client 与 Host 必须一致的四类字段；解释 before 为什么不可省。

第 3 节

练习

  1. 定位：在固定版本中找到 inject、source.subscribe、before.running、settings.section、form.set、unsubscribe、Host 的 Config、四条路由常量、connection.requestRejection，并各用一句话回答"它证明哪一环节"。
  2. 对照第 6 章：列出本案例与你在第 6 章写的最小插件之间，规模之外的两个结构差异（提示：多页面协调；配置命名空间的门控）。
  3. 自检：能否解释"运行结束"的判断为什么需要 before？if (!status.running) 会出什么错？

03

编写并加载
第一个插件

用 --patch 加载一份本地源码，第一次看到自己写的代码被 dsh 跑起来。

本章目标

  • 用 --patch 把一份本地源码加载进 dsh，并用日志验证。
  • 解释 apply 由谁调用，为什么不能用 node 直接运行插件文件。
  • 用 ctx.effect 正确清理自己创建的资源。

本章完整走通七环节图的第 2–3 格：加载与初始化。到本章结束，你将第一次看到"自己写的代码被 dsh 跑起来"的证据。

七环节

第 1 节

要解决的问题

怎样让 dsh 加载仓库里的一份本地源码？加载后插件什么时候执行、如何持续工作、卸载时如何清理？

本章用一个最小插件走完闭环：编写代码 → 配置加载 → 启动 dsh → 验证结果。不调用模型，没有界面。

第 2 节

核心概念

两个文件

文件作用
scratch-plugin/src/my-plugin.ts插件代码
scratch-plugin/cordis.yml告诉 dsh 从哪里加载这个插件

scratch-plugin 只是示例目录名，没有"放进去就自动加载"的作用。

插件模块的约定

插件模块导出两样东西：name（模块标识）和 apply(ctx)（加载入口，框架加载模块后调用并传入上下文 ctx）。

apply 不是你调的，是宿主调的。 所以不能用 node scratch-plugin/src/my-plugin.ts 验证——那没有 dsh 的上下文，也不会按插件机制执行 apply。

补丁里的字段与绝对路径

字段含义
insert向运行配置插入插件条目
id这个配置条目的标识
name要加载的模块路径

加载器解析 name 时以 profile 目录为基准，不是你执行命令的仓库根目录。写相对路径很容易指到 profile 里面去，所以本地开发路径必须写绝对路径。YAML 用空格缩进，不要混用 Tab。

清理：框架管的，框架管；你自己开的，你自己关

setInterval 这类原生资源不会因为写在 apply 里就被框架自动识别。ctx.effect 提供登记位置：回调里创建资源，返回的函数负责清理，插件卸载时框架调用它。

资源谁负责清理
ctx.on、ctx.tools.register 等框架注册随插件生命周期自动撤销
自建的定时器、网络连接、文件句柄必须写进 ctx.effect 返回的清理函数

1. 创建插件文件

Terminal
mkdir -p scratch-plugin/src

创建 scratch-plugin/src/my-plugin.ts：

TypeScript
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] 我的第一个插件已经加载')
}

2. 写加载补丁

先 pwd 确认仓库绝对路径，创建 scratch-plugin/cordis.yml（把路径换成你自己的）：

YAML
- insert:
    - id: hello
      name: '/Users/ada/projects/deepseek-harness/scratch-plugin/src/my-plugin.ts'

3. 启动并验证

Terminal
pnpm dsh web --patch ./scratch-plugin/cordis.yml

终端应出现：

输出
[hello-plugin] 我的第一个插件已经加载

这行日志说明第 2、3 格走通了：补丁被读取、模块被找到、apply 执行成功。它不表示已经增加了聊天工具或界面——日志在宿主终端，不在浏览器（第 7 格还没开始）。

4. 改一行日志并重启

Host 插件修改后通常要重启宿主：Ctrl+C 停止进程，重新执行带 --patch 的命令。刷新浏览器只重载 Client，不等于重载 Host。

5. 加入定时器

TypeScript
export function apply(ctx: Context) {
  console.log('[hello-plugin] 已加载')

  ctx.effect(() => {
    let count = 0
    const timer = setInterval(() => {
      count += 1
      console.log(`[hello-plugin] 运行检查：${count}`)
    }, 3000)
    return () => clearInterval(timer)
  })
}

重启后终端每 3 秒输出一次。本例直接结束整个进程时定时器随进程结束，这不等于验证了"运行中卸载的清理"；生命周期清理在下一章继续观察。

6. 停止加载

停止进程后执行 pnpm dsh web（不带 --patch），插件不再加载。取消加载配置即可停用，不需要删除源码。

7. 常见问题排查

现象优先检查
找不到 pnpm包管理器是否安装并加入命令路径
YAML 解析失败缩进、冒号和引号
找不到插件模块YAML 中是否为正确的绝对路径
没出现加载日志启动命令是否带 --patch
修改后仍是旧日志是否保存并重启了正确的进程
浏览器控制台没日志本例运行在 Host，看宿主终端

排查时先用只有一条日志的最小版本，确认加载成功后再加定时器，避免同时排查多个问题。

第 4 节

练习

练习 A（实现）：实现一个运行计数器——加载时输出"计数器启动"；每 2 秒输出当前计数；输出 5 次后停止；卸载时也能清理。

自检：计数到 5 时是否调用了 clearInterval？卸载时清理函数是否仍生效？

练习 B（定位题）：下面这份补丁是故意写坏的。不要改到能跑就收工——先用日志和现象定位它坏在哪一层（七环节图的哪一格），再改。

YAML
- insert:
  - id: hello
    name: 'scratch-plugin/src/my-plugin.ts'

提示：启动命令完全正确。观察报错指向哪里，再对照"加载器以 profile 目录为基准"解释原因。

第 1 节

Host 与 Client：代码在哪里运行？

使用 dsh 的 Web 界面时，系统至少涉及两个运行环境：

部分运行位置常见职责
Host：宿主端运行 dsh 的机器上的进程工具执行、文件访问、配置和服务
Client：客户端打开 dsh 页面的浏览器界面展示、点击交互、浏览器声音播放

以浏览器声音提醒为例的一种分工：

逻辑运行位置
提供任务运行状态Host
判断是否提醒Client（也可由 Host 判断后推送）
播放声音、显示设置界面Client
持久保存配置对应存储机制负责

逻辑放在哪一端，取决于数据在哪里、需要调用什么 API、希望谁负责执行。 两端不会因为变量同名就自动同步，必须通过通信接口交换数据。

两端 API 不同：Node.js 能用 node:fs、无 document；浏览器能用 document 和音频 API（通常需要用户手势才能启动播放）、不能直接用 node:fs。

文件访问的边界（重要）

直接调用 node:fs 会绕过 ctx.fs 文件服务，绕过绑定在该服务及相关钩子上的检查与策略。但用 ctx.fs 也不等于自动满足所有安全要求，仍需确认文件目标、调用上下文和实际启用的策略。

插件自带资源应相对模块或包根解析（如 import.meta.url），不要依赖 process.cwd()；用户工作区文件则通过 ctx.fs 或用户给出的路径访问。

第 2 节

路径：明确相对于哪里

位置含义
进程当前工作目录进程运行时使用的工作目录
模块所在目录当前代码文件的位置
用户工作区Agent 正在处理的项目位置

三者不一定相同：

JavaScript
await readFile('./message.txt', 'utf8')   // 相对进程 cwd
import { greet } from './greet.js'          // 相对当前模块文件

同样以 ./ 开头，解析基准可能不同。 插件资源、用户输入路径和宿主加载配置还各有解析规则，不能互相套用。第 3 章的"必须写绝对路径"就是这条规则的直接后果。

第 3 节

安装 ≠ 加载

操作作用
安装包将代码和资源放到可解析的位置
加载插件执行入口，注册工具、事件或界面等能力

包已安装却没有效果，按顺序问三个问题：宿主是否加载并执行了插件入口？profile 的 bundles 是否包含它？patch 是否插入了对应条目？

（profile、bundle、patch 的完整定义见第 5 章，此处先记住"安装之后还有加载这一关"。）

第 4 节

全书主图：插件的七个环节

插件从"一个想法"到"用户看到效果"，要经过七个环节。这张图是全书地图：

环节要确认的问题本课首次完整走通
1 安装包和相关文件是否存在？第 8 章
2 加载当前运行配置是否引用了插件？第 3 章
3 初始化入口是否执行，依赖是否就绪？第 3 章
4 注册工具、监听或界面是否成功注册？第 4 章
5 触发是否发生了预期的调用或事件？第 4 章
6 执行程序是否完成操作？第 4 章
7 展示结果是否返回到正确位置？第 6 章

怎么用这张图：

  • 学：每章开头标注处理哪几格，学完自查"这几格我能不能独立走通"。
  • 用：出问题时，先判断卡在第几格，再动手查那一格的证据。第 8 章会把这张图展开成完整排障流程。
  • 常见误区是跳格排查："没有听到提示音"直接改播放函数——但问题可能出在第 2 格（压根没加载）。

第 5 节

日志去哪里看？

代码位置日志通常出现在哪里
Host启动终端或宿主日志
Client浏览器开发者工具的 Console
安装、构建脚本对应命令的终端输出

按钮没反应先查 Client 与浏览器错误；入口没执行先查 Host 日志和加载配置。

第 6 节

练习

不写代码，回答：

  1. 一个 Host 插件和一个 Client 插件各自崩溃时，你分别在什么地方能看到错误？

  3. readFile('./config.json') 和 import x from './util.js' 里的 ./ 分别相对什么？

本章带走句

Host 干进程的事，Client 干浏览器的事；./ 相对谁要先问清楚；装上了不等于加载了。

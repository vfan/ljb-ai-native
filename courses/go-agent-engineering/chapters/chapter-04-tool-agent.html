一个回答，
可能经过多次调用。

把“查学生 → 查成绩 → 生成报告”拆成可观察的 ReAct 执行，并理解消息、会话、限制和失败边界。

先给模型一个行动

Tool Schema 是写给模型看的“工具参数说明”。

模型不会直接执行 Go 函数。它先根据 Tool 的名称、描述和参数结构生成调用请求，Eino 再把参数交给真实函数。

backend/internal/agent/tools/student_tools.go项目源码节选
func NewQueryStudentTool(svc *service.StudentService) tool.InvokableTool {
    return utils.NewTool(
        &schema.ToolInfo{
            Name: "query_student",
            Desc: "按学号、姓名、院系、专业或状态查询学生",
            ParamsOneOf: schema.NewParamsOneOfByParams(
                map[string]*schema.ParameterInfo{
                    "student_no": {Type: "string", Desc: "学号"},
                    "name":       {Type: "string", Desc: "姓名"},
                    "department": {Type: "string", Desc: "院系"},
                },
            ),
        },
        func(ctx context.Context, input *queryStudentInput) (string, error) {
            result, err := svc.List(repository.StudentQuery{
                StudentNo: input.StudentNo,
                Name:      input.Name,
                Department: input.Department,
                PageSize:  50,
            })
            if err != nil {
                return "", fmt.Errorf("查询失败: %w", err)
            }
            data, err := json.Marshal(result)
            if err != nil {
                return "", fmt.Errorf("序列化查询结果失败: %w", err)
            }
            return string(data), nil
        },
    )
}

先看项目锁定的版本

eino-oa 当前锁定 Eino v0.8.11，使用 flow/agent/react.NewAgent。新版官方示例也提供 ADK 的 ChatModelAgent 与 Runner。两者都在组织“模型选择工具 → 执行工具 → 把结果交回模型”的循环，但包路径和 API 不完全相同。实现时以项目的 go.mod 和对应版本文档为准。

消息闭环

Tool Call 和 Tool Result 都是对话的一部分。

Agent 并不是在模型外面偷偷执行一段代码。模型先返回结构化 Tool Call，Eino 执行工具，再把 Tool Result 追加到消息中交给模型。模型看到新结果后，才决定下一步。

sequenceDiagram
    participant U as 用户
    participant M as ChatModel
    participant E as Eino ReAct
    participant T as Tools
    U->>E: 生成张三的成绩报告
    E->>M: user message + tool schemas
    M-->>E: query_student(name=张三)
    E->>T: 执行查询学生
    T-->>E: student_id=1001
    E->>M: tool result
    M-->>E: query_grades(student_id=1001)
    E->>T: 执行查询成绩
    T-->>E: grades JSON
    E->>M: tool result
    M-->>U: 最终报告
消息谁产生作用
System应用定义角色和稳定规则
User用户表达当前目标
Assistant + Tool Call模型声明要调用哪个工具及参数
Tool Result工具运行时把真实执行结果交回模型
Assistant模型生成最终回答或继续调用工具

会话不等于长期记忆

历史消息让 Agent 看懂“他”“这门课”和“刚才那份报告”。

第二句话往往省略了第一句话已经说过的信息。模型不是天然记得上一轮，而是应用把同一会话中的历史消息再次传给了它。

连续对话案例

第一轮

用户：查询张三的数据结构成绩。

学业助手

张三的数据结构成绩是 72 分。

第二轮

用户：再分析一下他这门课的薄弱点。

历史消息提供的上下文

“他”指张三，“这门课”指数据结构。Agent 可以据此继续查询。但只有总分还不能判断具体知识点的薄弱处，需要题目或章节得分等额外记录。

读取同一 session→取出历史消息→追加当前问题→交给 Agent

只传第二句话

再分析一下他这门课的薄弱点。

“他”和“这门课”都没有明确对象，模型只能猜测或追问。

同时传入历史

查询张三的数据结构成绩。
再分析一下他这门课的薄弱点。

模型可以从上一轮解析代词，再选择下一步工具。

backend/internal/agent/agent.go · Chat项目源码
messages := make([]*schema.Message, 0, len(req.History)+1)
for _, h := range req.History {
    switch h.Role {
    case "user":
        messages = append(messages, schema.UserMessage(h.Content))
    case "assistant":
        messages = append(messages, schema.AssistantMessage(h.Content, nil))
    }
}
messages = append(messages, schema.UserMessage(req.Message))

resp, err := ca.agent.Generate(ctx, messages)
数据用途能否作为事实
当前消息本轮任务不能，仍要校验
会话历史理解上下文和代词不能，可能过期或包含模型错误
业务数据库学生、课程和成绩是当前业务事实来源

历史消息只帮助模型理解“用户在说什么”，不能替代业务数据库。即使上一轮说张三是 72 分，执行下一步关键操作前仍应重新查询，因为成绩可能已经更新，上一轮回答也可能出错。

历史越长，Token 成本越高，也可能把旧错误继续带入后续请求。真实系统需要限制历史长度，必要时摘要，并在关键动作前重新查询业务事实。

从浏览器到 Agent

浏览器先找前端服务，再由它转交后端。

Vite 是本地前端开发服务，Proxy 是请求转发。浏览器看见的页面和 API 都来自同一地址，就不涉及浏览器的跨域访问限制（CORS）。这与 Agent 选哪个工具是两个不同层次的问题。

flowchart LR
    B[浏览器 /api] --> V[Vite Dev Server :3000]
    V -->|proxy| G[Gin :8080]
    G --> H[Chat Handler]
    H --> S[Session Service]
    H --> A[Chat Agent]
    A --> T[Tools / Report Chain]
环境请求方式为什么不需要 CORS
本地开发浏览器请求 /api，Vite 转发到 8080浏览器只看到 3000 同源请求
正式环境Nginx 同域提供静态文件并转发 /api页面和 API 使用同一域名

仓库后端已经移除宽松 CORS 中间件。跨域不是默认能力；确实需要跨域时，也应只允许明确来源，而不是无条件返回 *。

循环必须有刹车

步数、超时、返回量和重试都要有上限。

MaxStep

防止模型在工具之间无限循环。eino-oa 当前设置为 10。

Context Timeout

模型调用、数据库查询和外部 API 都应响应取消信号。

Result Limit

查询学生默认最多返回 50 条，避免把大列表全部塞进上下文。

调用边界 · Go设计示例
ctx, cancel := context.WithTimeout(c.Request.Context(), 20*time.Second)
defer cancel()

reply, err := chatAgent.Chat(ctx, request)
if errors.Is(err, context.DeadlineExceeded) {
    return APIError{Code: "AGENT_TIMEOUT", Message: "任务执行超时"}
}

重试只适合明确的临时失败。例如新增成绩已经成功，但回复在途中超时，再重试可能新增两条。幂等键就是给同一次业务操作一个固定编号；服务端识别重复编号后返回已有结果，避免重复写入。

工具粒度

拆成多个 Tool，还是提供一个报告 Tool？

eino-oa 同时提供细粒度查询工具和组合式学生报告工具，这正好可以比较两种方案。

细粒度工具

query_student
query_grades
grade_analysis

可复用、过程透明；模型调用步数更多，组合结果更不稳定。

组合工具

student_report

内部调用 Report Service 与 Chain，流程和输出更稳定。

规则稳定、顺序固定的业务流程，优先放进 Service、Chain 或组合 Tool；需要模型根据现场信息选择路径时，再交给 ReAct 循环。

用户体验

只返回最终答案，长任务会像“卡住了”。

当前仓库的 Generate 调用只返回最终回复，适合第一版。任务变长后，可以把状态流式返回前端，但展示的是可理解的执行状态，不是模型的私有推理文本。

适合展示

正在查询学生
正在读取成绩
正在生成报告

不应直接展示

完整内部推理
数据库错误堆栈
Token 与敏感参数

本页总结

  1. Tool Call 与 Tool Result 都会进入 Agent 消息闭环。
  2. 会话历史帮助理解上下文，但业务事实必须重新查询。
  3. 开发环境通过 Vite Proxy 转发 API，后端不需要默认开放跨域。
  4. 稳定流程应下沉到 Service、Chain 或组合 Tool，不要全交给模型编排。
  5. 长任务可以流式展示状态，但不能暴露敏感信息和内部推理。

小练习

记录两次查询和一次停止。

  1. 输入“查询张三的成绩”，按顺序记录每个工具的名称、参数和返回值。
  2. 继续输入“他最低分的是哪门课”，检查“他”是否来自同一会话。
  3. 让查询工具返回超时，检查服务是否停止并说明失败。

完成标准：能区分模型发出的调用请求与工具实际执行结果；工具失败时，回答不补写成绩。

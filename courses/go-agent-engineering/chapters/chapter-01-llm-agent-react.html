先看三个对象

同样是“输入一句话”，能力边界完全不同。

对象它做什么典型结果
大模型根据上下文生成下一段内容回答、改写、总结、生成代码
网页对话把用户消息交给模型，再把模型回复展示出来你说一句，它回一句；能否查业务数据取决于背后是否接了工具
Agent让模型在对话中决定是否调用工具，并根据结果继续执行查学生、读成绩、计算指标、生成报告

一句话区分

网页对话是一种交互界面，背后也可以运行 Agent。判断是否能做事，要看程序是否连接了可执行的工具。 Agent 的底层仍然是消息对话，只是消息之间增加了结构化的工具调用和工具结果。

换个熟悉的例子

Cursor、OpenClaw 和我们的学业助手，本质上是同一类循环。

它们面对的工具不同，但基本结构一致：模型先判断下一步，再执行工具，读取结果后继续判断。差别不在“是不是 Agent”，而在工具集、权限和任务边界。

Agent模型负责推理什么执行什么工程边界
Cursor需要改哪些文件、怎样验证修改读取代码、编辑文件、运行测试工作区权限、命令确认、代码审查
OpenClaw如何使用外部能力完成用户任务调用已授权的 API、Skill 或自动化工具Token（访问凭证）、接口权限、调用记录
学业助手先找学生，再查成绩，再组织报告调用 query_student、query_grades 等 Tool用户身份、数据归属、只读与写入策略

不要把 Agent 理解成“会自己思考的网页”

Agent 的关键是推理与执行之间有程序连接。在本课中，Agent 通过工具查询业务数据；工具能做什么、谁有权调用，都由程序约束。

贯穿场景

“帮我生成张三的成绩报告”发生了什么？

如果既没有提供成绩，也没有连接查询工具，模型就没有生成真实成绩报告的依据。Agent 要先找到真实的张三，再读取他的成绩，最后基于工具返回的数据组织答案。

模型负责决定下一步；工具负责访问真实业务；每次工具结果都会回到对话上下文。

sequenceDiagram
    participant U as 用户
    participant M as 大模型
    participant A as Agent
    participant T as 业务工具
    participant DB as 业务数据库
    U->>A: 帮我生成张三的成绩报告
    A->>M: 用户消息 + 可用工具描述
    M-->>A: tool_call(query_student, name=张三)
    A->>T: 执行 query_student
    T->>DB: 查询学生
    DB-->>T: student_id=1001
    T-->>A: 结构化结果
    A->>M: 工具结果 + 原问题
    M-->>A: tool_call(query_grades, student_id=1001)
    A->>T: 执行 query_grades
    T-->>A: 成绩列表与统计数据
    A->>M: 最后一轮上下文
    M-->>U: 生成可读的成绩报告

执行模型

ReAct：判断下一步，执行动作，再查看结果。

ReAct 的名称来自 Reasoning（推理）与 Acting（行动）；每次执行后还要读取 Observation（观察结果），再决定是否继续。

这里的“推理”不是把模型内部思维全部展示给用户，而是让系统具备一个可观察的行动循环：模型提出动作，程序执行动作，再把观察结果交回模型。

只有一次回答

用户消息 → 模型 → 文本回复

“张三的平均分是 87 分。”

没有真实查询，答案无法核验。

ReAct 执行循环

用户消息 → 决策 → Tool → Observation → 决策 → 答案

query_student → query_grades → report

每一步都有输入、输出和失败边界。

flowchart LR
    Q[用户问题] --> R[Reasoning\n选择下一步]
    R --> A[Act\n调用工具]
    A --> O[Observation\n读取工具结果]
    O --> D{任务完成？}
    D -- 否 --> R
    D -- 是 --> F[生成最终回答]

看懂一次工具调用

模型提出“查谁”，程序负责“真的去查”。

Tool Schema（工具参数说明）告诉模型：工具叫什么、做什么、需要哪些参数。Tool Call（工具调用请求）是模型按这份说明填写的请求。下面用简化 JSON 展示两个方向的数据。

模型提出查询Tool Call · 示意
{"tool": "query_student", "arguments": {"name": "张三"}}

程序检查参数与权限后，调用查询服务，再把查询结果交回模型。

程序返回查询结果Tool Result · 示意
{"students": [{"student_id": 1001, "name": "张三"}]}

此时模型才有依据继续查询 student_id=1001 的成绩。若返回两个同名学生，应先澄清。第 4 章再用 Eino 代码实现这个过程。

第一轮工程评审

Agent 能调用工具，不代表可以随便调用工具。

问题当前案例的做法继续开发时要补什么
工具边界按学生、课程、成绩拆分工具每个工具只完成一个清晰动作，避免“万能工具”
返回结果工具返回 JSON 字符串统一成功/失败结构，避免把数据库错误直接交给模型
执行步数MaxStep: 10限制循环次数、超时和总成本
写入操作仓库中已有新增、修改、删除工具补充身份、权限、确认和审计，不能只因为模型说了就执行

能力扩展

ReAct 不只可以调用业务 API。

当前学业助手会调用 query_student 查询学生。把其他动作也做成工具后，模型就能用同样的循环完成更多事情。

Agent 想做什么可以使用的工具工具返回什么
查询学生调用 query_student学生数据
从教务网页查成绩查看页面、点击按钮、填写搜索框页面中的成绩
修改成绩前询问老师展示修改内容并等待确认同意或取消
分别查询和审核报告把查询交给一个 Agent，把审核交给另一个 Agent查询结果和审核结果
使用新接入的奖学金能力加载对应 Skill，再调用其中的 API奖学金规则或查询结果

变化的是工具，循环没有变化：模型选择动作，程序执行动作，结果返回模型，模型再决定下一步。

本页总结

  1. 大模型生成内容，网页对话传递内容，Agent 让模型在工具边界内完成任务。
  2. Agent 的底层仍是对话，只是加入了结构化 Tool Call、Observation 和多轮上下文。
  3. ReAct 是“决策 → 执行 → 观察 → 再决策”的循环，不是把一段提示词写得更长。
  4. 工具参数说明写清调用格式，程序负责校验和实际执行。
  5. 工具越接近真实业务，越要同时设计参数、权限、错误、超时和审计。

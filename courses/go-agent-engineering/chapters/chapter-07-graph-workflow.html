当前项目已经用 Chain 固定学生报告流程。本章继续比较 Graph 与 Workflow，判断项目复杂到什么程度才值得升级编排。

先认识边界，再决定是否改造

当前 eino-oa 没有 Graph 和 Workflow。学生报告的线性步骤用 Chain 已经足够；只有出现明确分支、并行、循环或字段级依赖时，才需要继续升级。

三种编排方式

编排就是安排步骤，并把数据交给需要它的步骤。

生成学业报告时，需要先准备数据、再生成内容；如果要查询多份资料，还要决定哪些查询可以同时进行，以及查询结果交给谁。Chain、Graph 和 Workflow 都在解决这类步骤安排与数据传递的问题。

方式怎么理解适合场景
Chain像流水线，步骤沿一条链向前，上一站的结果交给下一站填 Prompt → 调用模型 → 解析报告
Graph像路网，用节点和边表达路线；可以分支、并行，也可以循环按问题类型选择查询路径，或检查失败后重试
Workflow按依赖安排步骤，明确上游结果填入下游的哪些字段并行查询学生信息和成绩，再合并生成报告

这些方式并不是互不重叠：Graph 也可以表达线性或并行流程，Workflow 本身也是图。区别在于当前需求适合用哪种方式表达。这里的 Workflow 指 Eino 的 compose.Workflow：它不支持环；其他框架对 Workflow 的定义可能不同。

编排让全局结构可见

业务细节留在组件和 Service 中，编排负责表达步骤、依赖和数据如何传递。固定的线性报告流程已经在第三章用 Chain 实现；下面看需求变化后，Graph 和 Workflow 分别怎样表达。

Graph

Graph 像路网：在路口选择路线，也可以绕回来。

用户不一定每次都要求生成报告：他可能问成绩，也可能问培养方案。不同问题要查询不同的数据，因此先判断问题类型，再进入对应的处理路径。

flowchart LR
    Q[用户问题] --> C{问题分类}
    C -->|实时成绩| T[成绩 Tool]
    C -->|培养方案| R[规则 Retriever]
    C -->|通用解释| M[ChatModel]
    T --> A[生成回答]
    R --> A
    M --> A

每个处理步骤是一个节点，节点之间的连接是边。分类节点像路口：成绩问题走成绩查询，培养方案问题走知识库查询，最后整理成回答。Graph 的节点可以是 ChatModel、Retriever、ToolsNode、Lambda，也可以嵌套其他 Graph、Chain 或 Workflow。

如果需求改为“报告格式不合格时重新生成，最多尝试三次”，流程还可以从检查节点回到生成节点：

flowchart LR
    G[生成报告] --> V{检查格式}
    V -->|合格| O[输出报告]
    V -->|不合格且未超过次数| G
    V -->|达到次数上限| E[返回失败]

这条回边表达了循环。走哪条路线可以由代码规则判断，也可以由模型输出决定；使用 Graph 本身不意味着必须使用 Agent。

Workflow

Workflow 像准备报告材料：明确每份数据从哪里来。

生成报告需要学生基本信息和成绩。两项查询都需要学生编号，但彼此不依赖，因此可以并行；两份结果都准备好后，再交给报告生成步骤。

flowchart LR
    I[输入 StudentID] --> S[查询学生信息]
    I --> G[查询成绩]
    S -->|Student 字段| R[生成报告]
    G -->|Grades 字段| R

把报告输入想成一张待填写的表：Student 填学生信息查询结果，Grades 填成绩查询结果。Workflow 的字段映射就是明确“哪份结果填到哪里”。

Workflow 结构示意拓展案例，并非仓库文件
type ReportInput struct {
    StudentID uint
    Question  string
}

type ReportOutput struct {
    Answer string
}

workflow := compose.NewWorkflow[ReportInput, ReportOutput]()
workflow.
    AddLambdaNode("load_student", loadStudent).
    AddInput(compose.START, compose.FromField("StudentID"))
workflow.
    AddLambdaNode("load_grades", loadGrades).
    AddInput(compose.START, compose.FromField("StudentID"))
workflow.
    AddLambdaNode("generate_report", generateReport).
    AddInput("load_student", compose.ToField("Student")).
    AddInput("load_grades", compose.ToField("Grades"))
workflow.End().AddInput("generate_report")

这里的 FromField("StudentID") 表示取出输入中的学生编号；ToField("Grades") 表示把查询结果放进后续步骤的成绩字段。字段映射就是明确“哪份结果填到哪里”。

在这段示例中，两项查询分别从输入取出 StudentID；生成报告则等待并接收两路查询结果。Eino Workflow 的步骤按依赖向前，不支持回到前面形成循环。

Agent 还是 Graph

确定性流程交给编排，不确定选择交给 Agent。

问题优先方案原因
按固定顺序生成成绩报告Chain沿用第 3 章的线性流程即可
分别查询资料，再合并字段生成报告Workflow多路结果需要按字段汇总
用户意图不明确，需要决定查什么Agent模型需要根据上下文选择工具
按问题类型进入不同知识库Graph分支清楚，可测试和可观察
Agent 中执行稳定复杂流程Graph Tool模型只选择是否调用，内部流程保持确定

Agent 负责“选择什么”，Graph/Workflow 负责“选中之后稳定地怎么做”。

Graph Tool

把稳定的复杂流程包装成一个 Tool。

flowchart LR
    A[Agent] -->|调用 generate_report| GT[Graph Tool]
    GT --> S[并行查询学生与成绩]
    S --> V[校验数据]
    V --> G[生成报告]
    G --> GT
    GT -->|结构化结果| A

这样模型不需要编排每一个内部步骤，只需要判断是否调用报告工具。内部流程仍然可以并行、分支、记录 Callback，并单独测试。

中断、恢复与 Checkpoint

长流程需要在安全点暂停，并能从原位置继续。

Interrupt · 暂停

录入成绩前暂停，把参数展示给老师确认。

Checkpoint · 保存进度

保存流程状态，避免确认后从第一步重新执行。

Resume · 继续执行

带着确认结果从中断点继续，而不是开启一段无关新会话。

本页总结

  1. Chain 像流水线；Graph 表达路线、分支和循环；Eino Workflow 关注依赖与字段映射。
  2. 固定的线性步骤用 Chain；出现分支或多路数据依赖，再考虑 Graph/Workflow。
  3. Graph Tool 可以把复杂稳定流程交给 Agent 选择调用。
  4. 类型对齐、流式转换和 Callback 是 Eino 编排的重要价值。
  5. 写操作与长流程需要 Interrupt、Checkpoint 和 Resume。

小练习

给三项任务选择流程。

  1. 填提示词、生成报告、解析 JSON：画成一条顺序执行的链。
  2. 成绩问题查数据库，校规问题找文档：画出两个分支。
  3. 分别查学生和成绩，再一起生成报告：标出两路数据在哪一步合并。

完成标准：能解释选择 Chain、Graph 或 Workflow 的原因，指出哪些步骤可以并行、结果汇入哪些字段；知道 Eino Workflow 不支持循环，也不会因为出现多个步骤就直接增加 Agent。

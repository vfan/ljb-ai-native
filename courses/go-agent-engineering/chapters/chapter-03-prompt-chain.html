CHAPTER 3 · PROMPT / CHAIN / OUTPUT

03

先把一条固定流程做好，
再进入会自主决策的 Agent。

使用 ChatTemplate 管理 Prompt，用 Chain 串联模板与模型，并让输出变成业务代码可以继续处理的数据。

Prompt 也是代码资产

把固定规则和每次变化的数据分开。

Prompt（提示词）就是交给模型的任务说明与资料。ChatTemplate（消息模板）把固定文字留下，把姓名、成绩等可变数据留成待填的位置。

散落拼接

prompt := "分析学生：" + name + grades

角色、变量和规则混在一起，难以复用、测试和版本化。

模板管理

System + User + variables

消息角色清晰，变量显式，修改 Prompt 不必改动业务流程。

Prompt 应像 SQL、接口契约和配置一样被审查。尤其要区分稳定的系统规则、用户输入和外部数据，避免全部拼进同一段字符串。

ChatTemplate

给每次报告使用同一份模板。

下面的 {student}、{grades}、{gpa} 是变量位置，由程序填入学生、成绩和平均绩点数据。

backend/internal/report/report_prompt.go项目源码
func NewPrompt() *prompt.DefaultChatTemplate {
    return prompt.FromMessages(
        schema.FString,
        schema.SystemMessage(`你是学业分析助手。
只能依据程序提供的学生、成绩和 GPA 数据生成报告，不得补写不存在的事实。
只返回一个合法 JSON 对象，不要使用 Markdown 代码块。
JSON 必须包含 summary、strengths、weak_courses、next_actions 四个字段。`),
        schema.UserMessage(`学生数据：
{student}

成绩数据：
{grades}

GPA 数据：
{gpa}

请生成简洁、可执行的学业报告。`),
    )
}
内容放在哪里原因
角色与事实边界System Message每次调用都保持一致
当前任务User Message表达本轮目标
学生、成绩、GPA模板变量由程序显式注入并测试
数据库原始错误不进入 Prompt内部错误应由服务端记录和转换

Chain

Chain 像流水线：上一站的结果交给下一站。

用户说“给学生 123 生成一份学业报告”时，系统首先需要准备这个学生的数据。完整过程可以分成两部分：先由工具准备资料，再由 Chain 根据资料生成报告。

flowchart LR
    U[用户请求报告] --> A[Agent 选择报告工具]
    A --> T[student_report 工具]
    T --> S[查询学生信息和成绩并计算 GPA]
    S --> C[报告 Chain]
    C --> R[报告返回给 Agent 和用户]

Agent 根据用户请求选择调用 student_report 工具，并提供学生 ID。工具内部的 Report Service 再通过程序查询学生信息、成绩和 GPA。这些资料不是模型凭空写出来的，也不是模型在工具内部逐项决定查询的。

现在把视角放到资料已经准备好之后：报告 Chain 接收这些数据，先填好提示词，再交给模型生成内容，最后把模型返回的文字解析成程序可用的数据。

flowchart LR
    I[学生与成绩] --> P[ChatTemplate]
    P --> M[ChatModel]
    M --> J[JSON 解析与校验]
    J --> O[Report Result]

在这段报告生成流程中，数据沿着流水线向前走：上一站处理完，结果交给下一站。这些步骤的顺序固定，因此用 Chain 表达很自然。Chain 只负责完整任务中的这一段；外层仍然可以由 Agent 判断是否调用报告工具。

阶段数据怎样变化
输入学生信息、成绩和 GPA 等数据
ChatTemplate把数据填入模板，得到交给模型的消息
ChatModel根据消息生成包含报告内容的文本
解析与校验从文本中解析 JSON，得到程序可用的报告结果

例如，输入中有小明的数学成绩 85 分，模板会把这份数据放进报告任务说明；模型返回报告 JSON 文本；解析后，程序就可以分别读取总结和建议等字段。例子中的数据只是演示，报告仍应以实际提供的数据为准。

backend/internal/report/report_chain.go项目源码
func NewChain(
    ctx context.Context,
    chatModel model.BaseChatModel,
) (compose.Runnable[map[string]any, Result], error) {
    chain := compose.NewChain[map[string]any, Result]().
        AppendChatTemplate(NewPrompt()).
        AppendChatModel(chatModel).
        AppendLambda(compose.InvokableLambda(parseResult))

    runnable, err := chain.Compile(ctx)
    if err != nil {
        return nil, fmt.Errorf("编译学生报告 Chain 失败: %w", err)
    }
    return runnable, nil
}

这段 Chain 按“填模板 → 调模型 → 解析结果”的顺序执行。AppendLambda 接入普通 Go 函数，这里是 parseResult；Compile 将这些步骤组装成可调用的流程。这里的最终输出已经是 Go 的 Result，不是一段需要调用方自行猜测格式的文本。

结构化输出

让程序能分别取出总结、优势、薄弱课程和建议。

结构化输出就是把结果放进约定的字段。下面四个字段依次保存总体总结、优势列表、薄弱课程列表和后续建议。

backend/internal/report/types.go项目源码
type Result struct {
    Summary     string   `json:"summary"`
    Strengths   []string `json:"strengths"`
    WeakCourses []string `json:"weak_courses"`
    NextActions []string `json:"next_actions"`
}

JSON 不是自动可信

项目中的 parseResult 会截取 JSON、执行反序列化并检查 summary。结构化输出减少了解析歧义，但程序仍然必须校验模型结果。

接入项目

报告 Chain 最终仍然是 Agent 可以调用的 Tool。

flowchart LR
    A[ReAct Agent] -->|student_report| T[Student Report Tool]
    T --> S[Report Service]
    S --> D[查询学生 / 成绩 / GPA]
    D --> C[Report Chain]
    C --> T
    T --> A

agent.NewChatAgent 创建报告 Chain 和 Report Service，再把它注册为 student_report Tool。这样固定的报告流程由 Chain 保证，是否调用报告能力仍由 Agent 判断。

稳定性不是免费的

student_report 内部会额外调用一次模型，因此会增加耗时和 Token 成本。Token 是模型处理文字时使用的小单位，输入和输出的 Token 数通常参与计费。这里保留它，是因为正式报告需要稳定结构；普通查询仍然直接使用细粒度 Tool。

Chain 的边界

把固定步骤交给 Chain，把工具选择交给 Agent。

场景更合适的方式
成绩数据 → Prompt → 模型 → 报告Chain
根据用户请求决定是否调用学生报告工具Agent + Tool
调用报告工具后，查询数据并生成报告Tool + Service + Chain

本页总结

  1. Prompt 应被模板化、版本化和测试。
  2. ChatTemplate 保留消息角色并显式管理变量。
  3. Chain 适合稳定的线性流程，可以作为 Agent 调用的工具中的一部分。
  4. 结构化输出仍然需要程序校验。
  5. 步骤执行成功之后，还要核对报告中的事实。
下一章：流程不再固定时，让模型通过 Tool 和 ReAct 决定下一步。

小练习

检查一份“格式正确、事实错误”的报告。

给定成绩：数学 90 分、数据结构 72 分。模型返回合法 JSON，但把薄弱课程写成“数学”，并建议“弥补缺课”。

分别检查：字段是否齐全、薄弱课程是否与成绩一致、是否有缺课记录。写出至少一条格式检查和一条事实检查。

完成标准：能说明 JSON 解析通过仍可能答错；只能依据成绩提出建议，不能据此断言缺课或某个知识点不会。

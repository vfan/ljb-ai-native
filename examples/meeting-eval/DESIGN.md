# 设计说明：会议行动项评测平台

这份文档记录「为什么这样设计」，实现细节看代码与 [README.md](README.md)。

## 1. 目标与边界

课程给了一条很克制的主线：**先定义什么叫好，再用有代表性的输入验证，最后按失败原因改进产品。** 平台只服务这条主线，所以刻意收窄：

- 只做「会议行动项提取」一个任务，不铺成通用评测中台
- 只支持「单场景、单团队、小规模」，用单文件存储
- 只做提示词层面的版本对比，模型、参数、工具条件全部锁定
- 不做权限、多租户、CI 流水线、线上日志回流

判断标准也来自这条主线：平台不是团队规模的函数，而是「这次运行用了哪个版本、新版本改善了什么又引入了什么、结果能不能复核、哪些变化必须阻止发布」这四个问题是否需要反复回答。演示里这四个问题都出现了，所以需要平台；再往上加功能，收益就不明显了。

## 2. 评什么

### 2.1 输出契约

```json
{
  "action_items": [
    {
      "task": "完成接口改造",
      "owner": "小王",
      "due": "2026-03-20",
      "status": "pending",
      "evidence": "主持人：小王能不能下周五把接口改造做完？"
    }
  ]
}
```

`status` 是三种取值，而不是自由文本：

| 值 | 判定 |
|---|---|
| `confirmed` | 明确承诺、明确分派、已经确认 |
| `pending` | 询问、建议、试探，或缺少负责人/时间 |
| `cancelled` | 明确取消或暂缓 |

把「建议」和「承诺」压成一个布尔值，是这类产品最容易犯的语义错误。枚举值让这个区别在结构上就不可回避，也让规则评分有东西可查。

### 2.2 期望是约束，不是标准答案

课程强调「预期结果不一定是唯一的标准答案」。样本因此不存参考文本，而存可检查条件：

```json
{
  "items": [
    { "contains": ["接口改造"], "owner": "小王", "due": "2026-03-20", "status": "pending" }
  ],
  "allow_extra": false,
  "no_action": false
}
```

- `contains`：任务措辞可以不同，但必须命中主题词
- `owner` / `due`：`null` 表示「原文没有，输出必须留空」
- `allow_extra`：`change-2` 里「交接文档」是合理的额外行动项，不扣分
- `no_action`：`none-1` 只做情况通报，任何输出都是编造

这条设计直接决定了评分器不能做字符串比对，而要做「匹配 + 逐字段判定」。

### 2.3 硬门槛与质量分

硬性错误（任一触发即该条失败）：`fabricated_owner`、`fabricated_due`、`false_commitment`、`cancelled_as_todo`、`missed_item`、`wrong_owner`、`wrong_due`、`wrong_status`、`unsupported_claim`、`invalid_output`。

质量分只做展示，不参与放行：

```
quality = max(0, 100 - 10 × 软问题数 - 28 × 硬性问题数)
```

软问题包括措辞冗长、缺少原文依据、依据无法定位、已确认误标为待确认等。之所以把「已确认标成待确认」放进软问题，是因为它偏保守，业务损害远小于把待确认标成已确认。

硬性错误按「用例 × 类型」去重，同一用例里两条行动项都编造负责人也只算一个用例出错，避免错误数量被条目数放大。

### 2.4 测试集

14 条样本、6 个切片，全部来自课程列出的情境：

| 切片 | 条数 | 检验点 |
|---|---:|---|
| 正常表达 | 3 | 基础提取、多人多任务、相对日期 |
| 信息缺失 | 3 | 不补负责人、不补时间、不指定人 |
| 模糊承诺 | 3 | 询问、尽量、提议，都不能标已确认 |
| 决策变更 | 2 | 以最终日期/最终负责人为准 |
| 取消任务 | 2 | 取消要留痕，但不能变回待办 |
| 无行动项 | 1 | 空数组，不强行生成 |

这批样本偏边界，因此通过率不能当成线上真实分布；它衡量的是「已知的坑有没有踩」。

## 3. 怎么评

### 3.1 运行快照与单变量

一次运行固定记录：提示词 ID 与版本、模型名、温度、数据集 ID、重复次数、执行模式。提示词正文不原地修改，v1 与 v2 是两条独立记录。

界面上对比任意两次运行，但默认只帮你选「最近一次不同提示词的运行」作为基线，避免连续跑两次同一版本后自己和自己比。

### 3.2 评分流水线

```
样本 → 提示词 → 模型输出
                  ├─ 规则：结构 / 字段 / 日期 / 状态 / 证据是否可定位
                  ├─ 裁判：任务是否被原文支持 / 是否遗漏 / 是否误判承诺
                  └─ 合并：硬性错误取并集并按类型去重 → 通过 / 失败 + 质量分
```

日期归一化支持 `2026-03-20`、`3 月 20 日`、`下周五，待确认`，会按会议日期换算。依据校验用去标点后的包含关系，能挡住「编一段原文」。

### 3.3 裁判指令

课程给出的反例是「请评价这份整理结果，满分 100 分」。这里改成四个可复核的问题：

1. 任务是否得到原文支持，`evidence` 是否对应原文？
2. 负责人和截止时间是否明确，缺失时有没有被擅自补全？
3. 是否把询问、建议、试探标成了 `confirmed`？
4. 是否遗漏了原文中已明确确认的行动项？

要求逐条返回 `supported / status_correct / error_type / reason`，并强制引用原文片段。裁判结论不直接决定分数，而是映射成同一套错误类型，与规则结果合并去重。

回放模式下没有真实模型，裁判退化为本地启发式：检查证据是否真实存在、负责人是否在原文出现、承诺确认的句子附近有没有「能不能 / 尽量 / 看看」一类词。它比 LLM 裁判弱，但确定、可复现，足以跑通流程。

### 3.4 重复运行与一致性

`repeats` 支持 1–5 次。用例判定采用严格口径：**所有重复都通过才算通过**，同时记录「全部重复都通过」的稳定用例数。重复次数大于 1 时，单次抖动会直接体现为不稳定用例，而不是被平均掉。

### 3.5 回放与真实模式

- `EVAL_MODE=live` 且存在 key：调用 DeepSeek，记录真实延迟、token 与费用
- 否则：使用 `replay.go` 中的预置输出，延迟和成本按字符数模拟，界面标明「回放」

回放输出不是随机噪声，而是按每条样本的教学目的编排的失败模式。这样即使在无网络、无 key 的环境里，也能完整演示「对比 → 定位 → 门禁」链路。README 里明确写了这不代表真实模型测量结果。

## 4. 对比与门禁

### 4.1 指标口径

| 指标 | 口径 |
|---|---|
| 通过率 | 通过的用例数 / 总用例数（严格 pass@k） |
| 硬性错误用例 | 至少有一条硬性错误的用例数 |
| 错误分布 | 按错误类型统计用例数，同用例同类只算一次 |
| 平均质量分 | 各用例质量分的均值，仅作参考 |
| P50 / P95 延迟 | 所有模型调用的分位数 |
| 成本 | token 数 × 单价，按百万 token 估算 |
| 稳定用例 | 所有重复都通过的用例数 |

### 4.2 用例迁移

逐条比较基线与候选，分成四类：**修复**（失败→通过）、**保持通过**、**退步**（通过→失败）、**仍然失败**。对比页把退步样本排在最前面，点开就能看到原文、两次输出、规则检查项和裁判理由。

课程里的示例是「B 通过率更高、编造更少，但遗漏增加」。演示数据复现了同一个形状：v2 修掉 9 条，但 `normal-3` 从通过变成遗漏。

### 4.3 门禁规则

| 条件 | 结果 |
|---|---|
| 通过率 < 门槛，或硬性错误用例 > 上限 | `block` 阻止发布 |
| 退步用例 > 允许值 | `review` 需要人工确认 |
| 以上都不触发 | `pass` 可以发布 |

`review` 是独立状态，而不是「通过」的备注。这是刻意的：**通过率达标不等于可以发布**。

门禁结果是门槛与数据共同决定的。回放数据里 v2 是 13/14、只错 1 条，但有一条回归，所以显示「需要人工确认」；接真实 API 跑同一批样本时，v2 同样是 13/14、只错 1 条，但没有回归，默认门槛（允许 1 条硬性错误）就放行了。把允许的硬性错误改成 0，同一份结果会立刻变成 `block`。

这不是平台不一致，而是说明**阈值本身是产品决策**：漏掉一条已确认任务，对会议助手到底算不算不可接受，需要产品团队自己回答。

门禁按错误类型设限，不按总分，避免「格式分很高但编造了负责人」被平均掉。

## 5. 对象模型

| 对象 | 关键字段 | 不变式 |
|---|---|---|
| `Prompt` | id、version、body、notes | 版本不可变，改提示词就新增一条 |
| `Dataset` | id、kind（dev/holdout）、version | 验收集不参与调提示词 |
| `Case` | slice、transcript、meeting_date、expect | 期望是约束，不是参考答案 |
| `Run` | prompt_id、model、temperature、mode、repeats | 运行即快照，事后可解释 |
| `Result` | 原始输出、解析结果、规则、裁判、判定、耗时、成本 | 只追加，不原地修改 |
| `GateDecision` | baseline、candidate、thresholds、decision、reasons | 每次判定留痕 |

存储用单文件 JSON + 原子写（临时文件 + rename）。规模小时够用，接口与数据库一致；换 SQLite/Postgres 只需替换 `store.go` 的读写实现。

## 6. 界面

四个页面，对应四个必须反复回答的问题：

| 页面 | 回答的问题 |
|---|---|
| 运行 | 这次跑的是哪个提示词、哪个数据集？ |
| 版本对比 | 改善了什么，又引入了什么？ |
| 测试集 | 什么叫成功，哪些错误不能接受？ |
| 发布门禁 | 哪些变化必须阻止发布？ |

单条样本用右侧抽屉，而不是新页面：对比时最需要的是「原文和两次输出并排看」，抽屉保留了上下文。原文里会把模型给出的 `evidence` 高亮，编造的依据一眼就能看出来。

运行页的提示词卡片可以点开看全文，`{meeting_date}`、`{transcript}` 两个占位符会高亮；新用户第一次进入还会看到三步引导（选提示词 → 跑样本 → 看对比），跑过两次后自动收起。对比页的每个指标旁有「?」，用一句人话解释口径，避免把质量分当成发布依据。

## 7. 取舍与没做的事

- **只带验收集。** 演示没有单独维护调试集；真实项目里应先在调试集上迭代，再用验收集确认，避免「对着测试集改提示词」。
- **回放不是测量。** 回放数据是编排出来的教学样本，真实结论必须用 live 模式跑。
- **没有人工评审队列。** 结果保留了复核所需的检查项、错误类型、裁判理由和原文，但没有任务分派、标注一致性（如 Kappa）统计。
- **没有盲评。** 当前是单输出评分，不涉及 A/B 展示顺序；如果做两版输出对比，需要隐藏版本身份、交换顺序，并用人工标注校准裁判。
- **没有 CI 与线上回流。** `POST /api/runs` 可以被流水线调用，但拦截规则、失败重试、线上 bad case 入库都留给研发专题。

## 8. 接到真实业务时的下一步

1. 用真实脱敏会议替换 `seed.go`，补长输入、口语、缩写与多语言切片
2. 把调试集和验收集拆开，验收集只在发布前跑
3. 接人工评审：先标 100–200 条做裁判校准，再只复核硬性错误与争议样本
4. 把门禁接到 CI：候选版本跑验收集，`block` 直接拒绝合并
5. 线上把用户改过的字段回流成新样本，按失败类型补进对应切片
6. 把存储换成 SQLite/Postgres，补运行成本预算与提示词级别的成本对比
